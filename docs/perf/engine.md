## Against the targets

- Receive-to-present under one display frame (8.33 ms): p99 0.793 ms: **met**
- Under 1 ms CPU per frame: p99 0.712 ms: **met**

Indicative only (derived from DWM timing, not a target): 94.4% of new packets were presented before the first vblank after they arrived (1634 of 1731); the rest were shown one refresh later. DWM's reported vblank time can lag on a mostly idle desktop, so this estimate can read low. Either way no packet ever waits behind another: there is no queue.

Notes:
- Times are measured with `Instant`. "Receive" is when `recv_from` returned on the UDP thread; "present returned" is when `Queue::present` returned on the render thread.
- The vblank columns use DWM's composition timing (`DwmGetCompositionTimingInfo`) at present time. Waiting for the vblank is not engine work: it is set by the display refresh. Scan-out of the composed frame can add up to one more refresh on some display paths, which this method cannot observe.
- Only frames that showed a new packet count towards the receive series; CPU time counts every presented frame.

## Reproduce

```
cargo build --release -p fh6-app -p mock-udp
target/release/mock-udp --scenario bmw_m4_cs --duration 120 --rate-hz 60
target/release/FH6_WheelDash --bench-seconds 30 --bench-out docs/perf/engine.md
```
