## Live overlay

### After the host CPU phase (2026-11-27)

The same bench on the test PC (1920 x 1080 at 300 Hz, `mock-udp --scenario bmw_m4_cs`, stand-in game focused), with "CPU per frame" now the render thread's whole iteration less the frame-latency wait (known defect 17). Times in ms, p50 / p99.

| Cluster | Passes / draws per frame | CPU per frame | of which view + encoder + kit + `finish` | `Queue::submit` | `present` | Receive -> present |
|---|---|---|---|---|---|---|
| Bosch DDU | 2.9 / 13.5 | 0.656 / 0.873 | 0.248 / 0.359 | 0.140 / 0.203 | 0.218 / 0.333 | 0.662 / 1.366 |
| Liquid Glass | 4.0 / 14.9 | 0.684 / 0.883 | 0.283 / 0.407 | 0.139 / 0.199 | 0.216 / 0.308 | 0.688 / 1.537 |
| Aperture Nine | 3.0 / 11.0 | 0.623 / 0.783 | 0.235 / 0.318 | 0.132 / 0.184 | 0.211 / 0.300 | 0.626 / 1.288 |

What moved it: the render thread runs in MMCSS "Games" without power throttling and, on a hybrid CPU, on the performance cores (the tail fell by 0.2–0.3 ms); thin LTO; the kit's upload goes through a ring of mapped staging buffers instead of `Queue::write_buffer` (kit render 0.13 to 0.03 ms); bloom is one compute pass instead of nine render passes (about 0.045 ms). The dash's own work (build and draw) is about 0.03 ms. What is left is wgpu and the driver: about 0.25 ms to record and `finish`, 0.14 ms to submit and 0.22 ms to present. The compute bloom costs about 0.02 ms more GPU on bloom-heavy frames (Bosch DDU sequence p50 0.239 against 0.217 ms). Full report: [`engine.md`](engine.md).

### Phase 5 (before the host CPU phase)

`FH6_WheelDash --game-process fh6-stand-in.exe --config <cfg> --bench-seconds 25` with `mock-udp --scenario bmw_m4_cs` (60 Hz) and the stand-in game focused; no `--stats` overlay. Clusters that are still animating (springs, strobes) render every refresh, so the frame rate is about 106 fps at 120 Hz rather than the packet rate.

| Cluster | Frames | Receive -> present p50 / p99 | CPU per frame p50 / p99 / max | of which upload+record+submit p50 / p99 | `present` p50 / p99 |
|---|---|---|---|---|---|
| Liquid Glass sample | 2641 (105.6 fps) | 0.639 / 2.049 | 0.568 / 1.111 / 2.954 | 0.417 / 0.854 | 0.145 / 0.281 |
| Analog sample | 2653 (106.2 fps) | 0.571 / 1.836 | 0.493 / 1.123 / 2.621 | 0.338 / 0.797 | 0.148 / 0.347 |
| Liquid Glass + WGC refraction | 2642 (105.7 fps) | 0.655 / 2.039 | 0.581 / 1.192 / 2.945 | 0.428 / 0.945 | 0.144 / 0.302 |

Where the CPU goes: the kit's own work (recording the arena, packing the single upload, recording passes) is under 0.05 ms p50. The rest is wgpu: encoder finish and `Queue::submit` (about 0.07 ms plus 10 µs per pass), swapchain acquire bookkeeping and `present` (0.15 ms). The p99 sits around 1.1–1.2 ms. Phase 4's final bench (one pass, frames only on packets, `docs/perf/engine.md`) was 0.712 ms p99; the kit's 11–18 passes add about 0.1–0.3 ms of submit work, mostly visible in the tail. The p50 is about half the budget.

Levers for Phase 8 (not taken here, to keep the kit's look stable): a "performance" quality preset with bloom off (2 passes instead of 11–18; the analog sample then submits in 0.07 ms), merging the backdrop blur into fewer passes, and rendering only on new packets once springs settle (already done: `Cluster::animating`).

## Refraction source (Windows.Graphics.Capture)

`tools/wgc-bench --process fh6-stand-in.exe --seconds 5 --region 1300,1560,1240,560 --repaint` (120 Hz polling):

| Mode | Frames | CPU per delivered frame p50 / p99 / max | `latest()` per poll p50 / p99 |
|---|---|---|---|
| Pipelined, 2x downscale (620x280), the overlay's setting | 298 (59.6 fps) | 0.440 / 0.620 / 1.317 | 0.155 / 0.711 |
| Blocking, 2x downscale | 300 | 0.695 / 7.838 / 8.237 | 0.703 / 7.902 |
| Pipelined, full resolution 1240x560 | 299 | 0.579 / 0.802 / 1.373 | 0.479 / 0.882 |

Setup (D3D11 device, capture item, frame pool, session) takes 270–280 ms, so the overlay starts it outside the frame path and retries at most every 5 s. With capture on, the live CPU p50 rose by about 0.013 ms and p99 by about 0.08 ms. On the GPU the refraction sample is free (0.097 vs 0.096 ms). The image is one frame behind (pipelined readback). Capture is off unless `"GlassRefraction": true` is set in `config.json`.

## Glass layer, pass by pass (`bench-render --glass-spikes`)

RTX 3070 Ti Laptop (DX12), 3840x2160, a RetroCyber-sized panel (634,880 work px) with one flat optical-glass lens over it, 1000 frames per row in blocks of 50, interleaved, twice (28 Nov 2026, head 89f4aff). GPU ms from the kit's pass timeline (`Kit::set_gpu_timeline`); the three pacings (back to back, a 4K readback per frame as `preview-export` does, an 8 ms idle per frame as the overlay leaves the GPU) agree to within 0.003 ms.

| Variant | Frame p50 | p99 | Glass pass | Gap before it (copy, barriers) |
|---|---|---|---|---|
| no glass | 0.121 | 0.124 | - | - |
| glass layer with a plain fill (copy and segment only) | 0.167 | 0.171 | 0.028 | 0.018 |
| glass lens, one draw | 0.251 | 0.254 | 0.111 | 0.018 |
| glass lens as 9 clipped tiles | 0.258 | 0.262 | 0.118 | 0.018 |
| glass lens, rim band only (4 clipped strips, 48 px) | 0.184 | 0.188 | 0.044 | 0.018 |
| glass lens with backdrops off (same pass as the panel) | 0.219 | 0.221 | (in the panel pass, +0.098) | - |

- The layer itself (backdrop copy, a new segment and its target reload) costs about 0.046 ms; the optics shader over a panel-sized lens about 0.083 ms more.
- Trimming glass to its clip (PR #14) lets a lens be drawn only where it shows: the rim band alone saves 0.067 ms here. Tiling the whole lens costs 0.007 ms over one draw (the clip test at the seams), so tiles pay only when some are left out.
- Spikes: none. In 36,000 timed frames no frame was more than 0.022 ms over its row's median (a spike is +0.15 ms), in every pacing. The glass pass, the copy and the segment break do not stall in steady state.
